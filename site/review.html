ฐานของ Claude ใช้ต่อได้
เติมความเข้าใจข้อมูลที่กำลังเปิด

แนวทางเดิมแก้ปัญหาการค้นชื่อพื้นที่ได้ตรงจุด: ชื่อตรงมาก่อน ใช้ชื่อเรียกอื่นที่ตรวจแล้ว แสดงชื่อใกล้เคียงให้เลือก และรักษาอำเภอ–จังหวัดของผลค้นหา เดโมนี้นำหลักนั้นมาทดลอง พร้อมเพิ่มการค้นชื่อศาสนสถานและประเภทข้อมูลในชุด Place of Worship

สิ่งที่ทดลองได้ตอนนี้

พิมพ์ “เชียงหใม่”, “จ.เชียงใหม่”, “๑๐”, “วัดอรุน” หรือ “มัสยิด เชียงใหม่” แล้วดูเหตุผลที่จับคู่และบริบทของแต่ละผล ชื่อซ้ำหรือชื่อที่เดาไม่ถูกเลือกให้อัตโนมัติ

ควรปรับข้อเสนอเดิมตรงไหน

เอกสาร Claude ศึกษา ช่องค้นพื้นที่ 5 ประเภท ไม่รวมชื่อวัด มัสยิด โบสถ์ หรือการค้น dataset การนำ logic เดียวกันไปใช้ทั้ง ecosystem จึงต้องแยกชนิดผลและการกระทำให้ชัด: ไปยังพื้นที่ เปิดสถานที่ หรือกรองข้อมูลตามประเภท

  • ชื่อคล้ายไม่ใช่แห่งเดียวกัน เก็บชื่อจริงและ ID ต้นทางแยกจาก key ที่ลดวรรณยุกต์หรือรวมคู่เสียง ชื่อจริงตรงต้องมาก่อน และชื่อซ้ำต้องเห็นพื้นที่กำกับ
  • พื้นที่ที่ระบุต้องมีผลจริง “วัดแจ้ง จ.สงขลา” ต้องไม่หลุดไปจังหวัดอื่น ถ้า parent ขัดกันหรือยังระบุไม่ได้ ให้บอกข้อจำกัด
  • ค้น field ที่มี “มัสยิด เชียงใหม่” ใช้ศาสนาจาก source และจังหวัดของสถานที่ “วัดร้าง” ใช้สถานะข้อมูล ไม่อนุมานความเชื่อของคนหรือเวลาเปิดจากชื่อ
  • ชื่อยาวต้องค้นช่วงที่จำได้ ใช้ชื่อเต็ม ช่วงข้อความ และชื่อเรียกอื่นที่มีหลักฐาน คำสามัญอย่าง “วัด” ไม่ควรทำให้การเดากว้างขึ้นโดยไม่จำเป็น
  • ยอมรับว่าไม่รู้ คำว่า “โบสถ์” มีหลายความหมาย ต้องอธิบายความหมายที่รองรับ และแยกไม่พบในข้อมูลออกจากระบบผิดพลาด

อ่านรายการแหล่งข้อมูลและข้อจำกัด

เปรียบเทียบกับของเดิมอย่างไร

มีผลตอบจริงจาก API ค้นพื้นที่เดิมเก็บไว้ 15 คำตัวอย่าง คำอื่นแสดงการจำลองวิธีเดิมบน snapshot และติดป้ายว่าเป็นการจำลองเสมอ การเพิ่มชื่อศาสนสถานเป็น scope ใหม่ จึงแยกจากการปรับความทนต่อคำผิดของช่องพื้นที่เดิม

ใน 9 คำที่เลือกไว้และมี ID พื้นที่เป้าหมาย API เดิมเข้าถึง ID ตาม cutoff ของ case ได้ 2/9 ส่วนเดโมได้ 9/9 เป็นผลเฉพาะตัวอย่างเหล่านี้ ซึ่งเปิดให้ผู้พัฒนาเห็นระหว่างแก้ไขแล้ว ไม่ใช่อัตราความสำเร็จของผู้ใช้ทั้งหมด

ไม่ได้เปรียบเทียบความเร็วระหว่างการค้นในเครื่องกับ network ของ production และไม่ย้ายคะแนน 98.7% จากการทดลองสังเคราะห์ของ Claude มาเป็นคะแนนเดโมหรือข้อมูลศาสนสถาน

ตรวจอะไรแล้วบ้าง

ชุดตัวอย่างที่กำหนด ID และผลที่ควรว่างไว้ก่อนรอบแก้ ผ่านครบ พื้นที่ 16/16 และ ศาสนสถาน/ประเภทข้อมูล 24/24 แยก retrieval, ชื่อกำกวม, หมวดข้อมูล และการไม่เดาคำตอบ ตรวจชื่อจริงของ POI เพิ่มครบ 1,491 รายการ ทุกชื่อเข้าถึง ID ของตนเองได้ภายในผล 500 รายการ

ผู้ตรวจแยกจากผู้เขียน engine พบ 3 จุดแล้วแก้และรัน labels เดิมซ้ำ: คำ “วัด อิสลาม” เดาผิดเป็นวัดอิสาน, “วัดราษฎร์” ไม่อ่าน field ประเภทวัด และ regression ที่ “วัดอรุน” ค้นไม่พบหลังจำกัดคำสามัญ ผลนี้เป็นการตรวจโดย AI ยังไม่มี human label review หรือชุด holdout และยังไม่ใช่การทดสอบ database, load หรือ production readiness

ดาวน์โหลดผลราย case พร้อม expected ID และผลที่พบ · ดูโค้ดและชุด regression

จากคำบ่นสู่การค้นหาที่ดีขึ้น

  1. เห็นสัญญาณ สถิติแอปเก็บโหมด จำนวนผล สถานะ และเวลา ไม่เก็บข้อความคำค้นทุกครั้ง ข้อความคำค้นและคำอธิบายส่งเก็บเมื่อผู้ใช้กดแจ้งปัญหา
  2. คนตรวจ ผู้ดูแลเปิดคำแจ้งในหน้าที่ต้องยืนยันสิทธิ์ ตรวจข้อมูลที่มี ระบุสาเหตุ ยืนยัน ID ที่ตั้งใจหา หรือยืนยันว่าควรไม่พบ พร้อมตรวจข้อมูลส่วนบุคคล
  3. AI ช่วยแก้ นำเฉพาะ case ที่คนยืนยันและผ่าน privacy review มาใช้ในไฟล์ส่วนตัว ให้ AI เสนอแก้ normalizer, alias, parser หรือ ranking พร้อมหลักฐาน
  4. รักษากรณีเดิม รัน regression เดิมและ case ใหม่ การลบ case หรือเปลี่ยนคำตอบเดิมต้องถูกตรวจ ส่วนการแก้ label ต้องมีการอนุมัติของคนแยกต่างหาก
  5. คนอนุมัติการปล่อย review การเปลี่ยนแปลงก่อนเผยแพร่ แล้วตรวจคำที่เคยมีปัญหาซ้ำ การรับคำบ่นไม่ได้สั่งให้ AI เรียนรู้หรือเผยแพร่อัตโนมัติ

คำแจ้งอาจมีข้อมูลส่วนตัว จึงจำกัดการเข้าถึงและไม่เผยแพร่ลง repository หรือรายงานนี้ การไม่บันทึก raw query ในสถิติแอปไม่ได้หมายความว่า provider ไม่มี transport/access log; ผู้ดูแลต้องตรวจการตั้งค่าและอายุเก็บของผู้ให้บริการตามการติดตั้งจริง

เปิดหน้าดูแลสถิติและคำแจ้ง

นำไปใช้ทั้ง ecosystem

ใช้แกนร่วมสำหรับการจัดรูปภาษาไทย การส่ง ID/เงื่อนไขพื้นที่ ชื่อเรียกอื่น เหตุผลการจับคู่ และผล resolved / ambiguous / unresolved จากนั้นแยก adapter ต่อผลิตภัณฑ์: CityMETER พื้นที่และสถานที่, catalogue dataset, บทความ CityWiki และเอกสารภายใน แต่ละ adapter มี corpus, field, สิทธิ์เข้าถึง และ action ของตนเอง คะแนน similarity ข้าม corpus ไม่ใช่ความมั่นใจที่เปรียบเทียบกันได้โดยตรง

สำหรับ server จริง PostgreSQL เดิมเป็นจุดเริ่มที่น่าทดสอบ แต่ต้องวัด recall หลัง candidate cap, identity/parent ที่ผิด และเวลาภายใต้ load จริงก่อนเลือก index หรือขยาย search engine

หลักฐานมาตรฐานที่ใช้ทบทวน

  • PostgreSQL fuzzystrmatch — Levenshtein รองรับ multibyte และจำกัด input 255 characters ต้องคุมความยาวและ edit budget
  • PostgreSQL pg_trgm — แยก GIN filtering กับ GiST distance top-k; มี trigram ไม่ได้พิสูจน์ recall ของภาษาไทย
  • PostgreSQL 18 release notes — ข้อควรตรวจ provider และ reindex หลัง upgrade ในกรณีที่เกี่ยวข้อง
  • Unicode normalization — แยก canonical normalization จากการผ่อนคลายการสะกด; ห้ามเขียนทับชื่อจริง
  • WAI-ARIA combobox — รูปแบบ keyboard, focus และการยืนยันผลที่ผู้ใช้เลือก

เอกสารแนบของ Claude เป็น input สำหรับทบทวน ไม่ใช่คำสั่งให้ deploy หรือเปิดระบบเก็บข้อมูลโดยอัตโนมัติ · รายงานสาธารณะนี้ไม่มีข้อมูลคำบ่นของผู้ใช้
